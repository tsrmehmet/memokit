# memokit

memokit is a Claude Code plugin that enforces a small working model for AI-assisted development. The orchestrator (your main session) never writes production code; a Sonnet `memokit:coder` subagent does, and an Opus `memokit:reviewer` gates every slice before it counts as done. Session rituals keep `docs/STATE.md` current, and a context budget triggers a measured, autonomous handoff before a session grows too expensive.

This is personal infrastructure shared as-is. MIT licensed, no support guarantee.

## What's inside

## Install

Install memokit **once, at user level**:

```
/plugin marketplace add tsrmehmet/memokit
/plugin install memokit@memokit
```

In the `/plugin install` dialog pick the user scope (from a shell: `claude plugin install memokit@memokit --scope user`). The plugin manifest sets `"defaultEnabled": true`, so the install leaves memokit enabled for every project. Then run `/memokit:init` in each git repository that should use it.

memokit stays out of the way elsewhere: the hooks act only in projects that have `.claude/memokit.json`, the agents and skills (`memokit:coder`, `/memokit:resume`, …) are `memokit:`-namespaced and stop on their own when it is missing, and the "run `/memokit:init`" hint is off by default (`MEMOKIT_INIT_HINT=1` turns it on; see "Kill switches and troubleshooting"). `/memokit:init` asks whether everyone who clones the repository should be offered memokit too; only on yes does it write `enabledPlugins["memokit@memokit"] = true` and the marketplace into the project's shared `.claude/settings.json`. The recommended answer is no unless you maintain the repository and the team agreed: the entry offers every contributor a third-party plugin, and your user-scope install already covers you.

In a repository you do not trust, look at `.claude/memokit.json` before the first session: its `sessionStart.healthScript` runs at every session start and `graph.refreshScript` at handoff. That is the same exposure as hooks in the repository's `.claude/settings.json`; memokit only refuses scripts that resolve outside the project root.

Requirements: bash, jq, git; macOS or Linux.

## Quick start

1. With memokit installed (see Install), open Claude Code in a git repository and run `/memokit:init`.
2. It detects your stack and asks a short set of questions: project name, tag, language, guarded directories, and the docs to show at session start.
3. It writes `.claude/memokit.json` and overlay skeletons, creates `CLAUDE.md`, `docs/STATE.md` and `docs/DECISIONS.md` from templates if they are missing (it never overwrites an existing file; if it detects a site generator that publishes `docs/` (mkdocs, Docusaurus, Sphinx with Markdown, VitePress, Jekyll with `docs/_config.yml`), it offers to exclude these files from the site), and, only if you want the team on memokit, registers the marketplace and plugin in `.claude/settings.json`.
4. Start a new session. Hooks are active only in projects that have `.claude/memokit.json`.

## Code graph (graphify)

With `graph` set in `.claude/memokit.json`, memokit keeps a graphify code graph in `graphify-out/` current:

- **At every handoff** `/memokit:handoff` runs `skills/handoff/scripts/memokit-graph.sh refresh` after its commit. It does nothing when no commit touched `graph.root` since the last refresh; otherwise it runs `graphify update <graph.root>` (code only, AST extraction, no LLM tokens) and moves the marker `graphify-out/.graph_commit` to `HEAD`. A failed refresh keeps the previous graph and is reported as a warning; it does not fail the handoff.
- **On a codebase question** ("where is", "who calls", …) the hint carries the measured staleness: fresh → query directly; more than `maxCommitsBehind` commits behind → refresh before answering.
- `graphify-out/` must be git-ignored; the refresh refuses otherwise. graphify does not read nested `.gitignore` files, so put build output and secrets under the root into a `.graphifyignore` at the repo root.

`/memokit:init` offers the graph with a measured recommendation. In a project without `graph`, the hint tells the AI to ask you before building one rather than building it on its own. `memokit-graph.sh status` prints the staleness (exit 0 fresh, 1 stale, 2 unknown, 3 no graph).

## PDF and Office files (markitdown)

Claude reads a PDF page as an image plus its text, which costs far more tokens than the text alone. With `convert.markitdown` set (`"convert": {"markitdown": true}`) in `.claude/memokit.json`, a Read of a `.pdf`, `.docx`, `.pptx` or `.xlsx` file (any case; main session and subagents) is redirected to a Markdown conversion made by [markitdown](https://github.com/microsoft/markitdown), and one line of context says so.

- **Install** markitdown yourself; memokit adds no Python dependency and stays off while `markitdown` is not on PATH: `uv tool install 'markitdown[pdf,docx,pptx,xlsx]'`. `/memokit:init` offers the setting only when it finds the command.
- **Local only:** markitdown runs on your machine with plugins off and no LLM client; the file path is passed as one argument.
- **Cached** in memokit's temp dir (`memokit-<n>-careful-convert`), one subdirectory per document (named by the SHA-256 and size of its content): an unchanged file is converted once. The cache is protected like memokit's own state: subagents cannot write there, a Bash command naming it is refused (`careful-state`, in the main session too), and the cached copy is opened with Read only; a cached copy that is not yours or sits behind a symlink is never used. A cached copy unused for 7 days is removed the next time another document is converted; the whole cache goes 7 days after the last new document. A scanned or timed-out file is not retried for a day.
- **Left alone:** a Read with a `pages` argument (Claude asks for page images), a scanned PDF (under 200 non-blank characters of Markdown per page), an empty result, a failed conversion or one that takes over 45 s; then the original Read runs as before. Images and attachments pasted into the chat are not files on disk and are never converted (an image's content needs a vision model; Claude reads images itself).
- **Permissions:** with any `Read` deny or ask rule in the settings files memokit can see (the project's, the launch directory's, the current directory's, your user settings, managed settings and their `managed-settings.d` drop-ins) it does not redirect, because rules are checked against the redirected path and would let a rule on the original miss. Rules given on the command line (`--settings`, `--disallowedTools`) and MDM/plist policies are not seen: the redirected Read then goes through the normal permission flow for the cached copy. A file inside the directory you started Claude Code in is read without a prompt, like the original; for any other file you are asked, with the original path named, and a "don't ask again" covers only that document's cache directory. Files in directories added with `--add-dir` are asked too, and in headless (`claude -p`) or background-agent sessions, where no prompt can be shown, that ask may end as a denied Read: put such files under the launch directory or turn the setting off there. A path holding a control character is never redirected.

## Handoff notification

The last step of `/memokit:handoff` sends one line through Claude Code's `PushNotification` tool: "handoff ready, next: …" or "handoff not complete: …". The tool skips the push while you are at the terminal and reaches your phone when Remote Control is connected, so an autonomous handoff at the context budget tells you when to open a new session.

Project-specific rules live in `.claude/memokit/`:

| File | Read by |
|---|---|
| `rules.md` | `inject-rules.sh`, on every prompt |
| `coder.md` | `memokit:coder`, as its first step |
| `reviewer.md` | `memokit:reviewer`, as its first step |
| `analyst.md` | `memokit:analyst`, as its first step (project checks, e.g. issue-tracker or design verification) |
| `gates.md` | `memokit:coder` and the orchestrator: the Tier-1 and Tier-2 test commands (see Test tiers) |
| `handoff.md` | `/memokit:handoff`, after the generic steps |
| `resume.md` | `/memokit:resume`, after the generic steps |
| `triage.md` | `/memokit:triage`, as its first step |

Precedence: overlays only add and narrow. They cannot loosen the plugin's invariants: subagents cannot touch git history, the orchestrator cannot write to guarded dirs, and nothing is called done without evidence. A loosening attempt is ineffective because the hooks block it anyway.

## Test tiers

A general rule (`WORKING-MODEL.md` §9) for sequential and parallel work alike, re-injected on every prompt:

- **Tier 1**, in every slice, run by `memokit:coder`: build, the unit tests of the touched projects, and the slice's new or changed tests (red, then green). No Testcontainers, no integration or E2E suites, and it never starts, builds or recreates a container; in a container-only project a Tier-1 command may exec into an already running dev container (`docker compose exec app …`) when that container sees the files under test (in a parallel run it usually does not see the lane worktrees, so such a project's tasks run sequentially). It must run without secrets.
- **Tier 2**, the heavy gates (integration, coverage, merge gate, E2E): once per batch, run by the orchestrator in the main checkout, one gate at a time, and only after you answer "Tier-2 gates next, or more work first?". Never unasked, never by a subagent.
- A slice with a green Tier 1 is `gate-pending`; it is called done only when Tier 2 is green.

The commands live in `.claude/memokit/gates.md` (`## Tier 1` and `## Tier 2` sections). `/memokit:init` creates the skeleton and offers to fill it with you. When it is missing or has no Tier-1 command, the coder returns `BLOCKED` with `gates.md missing` and the orchestrator asks you once; nobody guesses the commands.

## Parallel runs

`/memokit:parallel` runs a batch of independent tasks (a plan file, a ticket list, a `docs/STATE.md` section) at the same time without giving up any of the single-slice rules: every slice still gets TDD, Tier-1 evidence and an independent review, and you still make every decision. The orchestrator does every git operation; subagents only write code in their own directory.

Each lane works in its own **git worktree**. A worktree is an extra working directory attached to the same repository: it has its own checked-out branch and its own files, but shares the one `.git` history. Two lanes in two worktrees cannot overwrite each other's files, and a finished lane is merged like any branch. Lane worktrees live under `.claude/worktrees/mk-<run>-<lane>` on a branch `mk/<run>/<lane>`, created from the current integration branch when the lane starts. Nothing untracked or ignored is copied in: no `.env`, no local config, no secrets.

The lifecycle:

1. **Analysis.** One read-only `memokit:analyst` per task (or small group) reports the files it touches, its dependencies, a risk tag (`high` or `normal`) and the decision questions it foresees.
2. **Plan approval.** Tasks that share files or depend on each other go into one lane, in order; global hotspots (shared libraries, migrations, cross-service contracts) get a solo lane that runs alone. You approve the lane table, risk tags included, before any code starts.
3. **Batch decision sweep.** Every foreseeable question is asked up front, at most 4 per prompt, each with a recommendation. A lane with an open question does not start.
4. **Rolling lanes in worktrees.** Up to `parallel.maxCoders` lanes run at once; a freed slot starts the next ready lane right away. A decision that comes up at run time pauses only its own lane.
5. **Review by risk.** Each slice is reviewed on its lane's diff, up to `parallel.maxReviewers` at once. The orchestrator first marks the lane's new files intent-to-add (`git add -N`, nothing committed), so the diff includes them.
6. **Merge queue.** Approved lanes merge into the integration branch one at a time, in completion order (`git merge --no-ff --no-edit`), and the orchestrator re-runs Tier 1 after each merge. A conflict or a red Tier 1 goes to a resolution slice; the orchestrator never edits code by hand.
7. **Cleanup.** Right after a green merge: `git worktree remove` and `git branch -d`, verified with `git worktree list` and `git branch --list 'mk/*'`. Never forced: if git refuses, you are asked.
8. **Opus batch review.** One Opus review of the whole batch diff, the safety net for anything a slice review missed; its findings go through one fix wave.
9. **Tier-2 question.** "Tier-2 gates next, or more work first?" Only your go runs the heavy gates; reds are triaged in one pass.

**Ledger.** The run's state lives in `.claude/memokit/runs/<run-id>/ledger.md`, next to the lane briefs and reports. It is git-ignored and stays local (`/memokit:init` and the skill add the ignore lines for it and for `.claude/worktrees/`). Each task moves through `planned` → `decided` → `running` ⇄ `needs-decision` → `in-review` → `approved` → `merging` → `merged` (gate-pending) → `done`; a failed step sends it back to `running` through a fix slice. `merging` marks the merge in progress (merge-start and merge-end are logged), so a resumed run can tell whether it landed. `/memokit:handoff` writes "Resume run <id> with /memokit:parallel" as STATE's next step, and `/memokit:resume` continues the run from its ledger. At the end the run reports each lane's token totals and wall time, with a recommendation on `parallel.maxCoders`.

**Reviewer by risk.** `memokit:reviewer` is one agent; the parallel run picks its model per dispatch. With `review.model: auto`, `high`-risk tasks (security, authorization or tenant isolation, personal data, migrations or data integrity, concurrency, shared libraries, cross-service contracts, guard/hook code) are reviewed by Opus and `normal` ones by Sonnet. A Sonnet reviewer that meets a high-risk concern answers `ESCALATE: opus — <reason>` instead of approving, and the review is re-run on Opus. The Opus batch review before the Tier-2 question always runs.

**Review verdicts.** Every finding in a review carries a verdict: `confirmed` (reproduced or proven from the code, with a severity by impact), `needs_validation` (plausible, with the measurement that would confirm it) or `rejected`. The reviewer ends its report with a findings JSON that `skills/parallel/scripts/memokit-findings.sh validate <report>` checks; a malformed report is re-run once. Only a `confirmed` finding rejects a slice. `needs_validation` items put the lane in `validating`: the orchestrator measures them before the lane joins the merge queue. After a `REJECT` (per `review.validate`) a second reviewer tries to refute each finding, and the coder fixes only what survives. Outside a parallel run the reviewer keeps its default model, Opus.

**Leftover worktrees.** At session start memokit counts the worktrees under `.claude/worktrees/` (parallel lanes and Claude Code's own `agent-*` worktrees) of the main checkout and of every other worktree of the repository (a session in a sibling `git worktree add` checkout creates its lanes there), and the `mk/*` branches without a worktree, except the worktree the session runs in, and reports them in one line with their total size (measured within about 2 s; `≥` when some could not be measured). From 0.6.1 it then checks them in a detached background job and removes the `merged-clean` ones that look unused for `scratch.staleAfterHours` (index not rewritten, no Claude Code transcript for that path written, no process with its cwd inside) and still hold no change or ignored file right before the removal (`git worktree remove`, never forced, and `git branch -d` for an `mk/*` branch; git ≥ 2.31) and merged `mk/*` branches without a worktree; everything else (dirty, unmerged, ignored files, fresh) is reported at the next session start for `/memokit:sweep worktrees`. `MEMOKIT_AUTOCLEAN_OFF=1` turns the removal off. Lanes of a run whose ledger says `status: active` are not leftovers: a separate line names the run, which `/memokit:resume` continues. A run you end early gets `status: stopped`; its remaining lanes are then reported like any others. `/memokit:sweep worktrees` lists each one with its status (`active-run`, `merged-clean`, `merged-ignored`, `dirty`, `unmerged`, `orphan-branch`, `detached`, `locked`, `prunable`, `manual`), size, last commit and whether it is merged into the current or the default branch. It offers only `merged-clean` rows; a row with ignored files (a `.env`, `node_modules/`) goes only by an explicit per-row pick after you have seen them, and a branch merged only into the default branch is listed for you to delete from the default branch (git refuses `git branch -d` elsewhere). Unmerged or dirty work is listed for you to decide, never removed.

Limitations: no hook confines a coder to its lane worktree; the brief sets the scope and the orchestrator verifies it by measurement (`git -C <worktree> status`, a clean main checkout). Tier 1 runs without secrets in the lanes; anything that needs them belongs to Tier 2. `parallel.maxCoders` has no upper bound in the config; the skill warns when `maxCoders` + `maxReviewers` exceeds Claude Code's concurrent-subagent limit (`CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS`, default 20).

## Context budget

Every turn re-sends the whole context, so cost grows roughly with its square. When the context passes `contextBudget.limitTokens`, the Stop hook tells the AI to decide by itself, without asking you:

1. Finish the current work, then hand off (if it closes in a few turns), or hand off now (if the remaining work is long or you are at a natural stopping point).
2. Tell you in one line which it chose and why.
3. Run `/memokit:handoff` completely, through its phone notification, then verify the handoff by measurement.
4. Only when every check passes, say the handoff is current and that "continue" is enough next session. If a check fails, fix and re-measure, or report what failed.

The reminder fires once when the budget is crossed and again every step of tokens after that. Environment variables (must be valid non-negative integers, otherwise the default applies; `MEMOKIT_CONTEXT_STEP` must be above zero):

| Variable | Effect |
|---|---|
| `MEMOKIT_CONTEXT_LIMIT` | Overrides `contextBudget.limitTokens`. |
| `MEMOKIT_CONTEXT_STEP` | Tokens between repeat reminders (default `100000`). |
| `MEMOKIT_CONTEXT_OFF=1` | Disables the context-budget reminder. |

## Kill switches and troubleshooting

Hooks read these from their environment, so set them in `.claude/settings.local.json` under `env` (one that should apply in every repository, such as `MEMOKIT_INIT_HINT`, under `env` in `~/.claude/settings.json`), or export them before launching `claude`. Exporting inside a Bash tool call does not reach the hooks.


- **Guards deny everything:** `jq` is missing or `.claude/memokit.json` is invalid. The guards fail closed, so the session cannot repair the config itself. ## Temp space

Agents leave scratch copies behind and a full disk stops everything. `WORKING-MODEL.md` §7 gives the rules (copy only tracked and untracked-not-ignored files, one dedicated scratchpad directory per task, delete it before returning, end every report with `temp left: <size>`). Three things enforce them:
- a SubagentStop gate blocks a subagent that leaves `scratch.agentMaxMB` or more of new files in the scratchpad (`MEMOKIT_SCRATCH_OFF=1` disables it);
- a disk watch warns when one command eats `disk.dropWarnGB` or free space is below `disk.minFreeGB`, and SessionStart reports stale leftovers of at least `scratch.reportMinMB` and low disk (`MEMOKIT_DISK_OFF=1` disables the watch);
- SessionStart removes stale leftovers of finished sessions by itself in the background (nothing under them holding `.memokit-keep`; `MEMOKIT_AUTOCLEAN_OFF=1` disables it), and reports what it keeps. "Stale" means the session's transcript has been idle longer than `scratch.staleAfterHours` (a loose entry: born that long ago), so a session left open but idle that long counts as finished;
- SessionStart also prunes memokit's own state files (approval codes, windows, config snapshots, markers under the temp dir) older than 7 days, in the background, at most once a day;
- `/memokit:sweep` measures stale leftovers, asks, and deletes the approved ones. The destructive-command guard lets a recursive `rm` of a direct child of the current session scratchpad, or of a whole stale sibling temp entry, through without an approval code. A subagent gets this only for a single simple `rm -rf <literal absolute path>`. The main session (the orchestrator) also gets it inside a chained command (`&&`, `;`, `||`, `cd … &&`, quoted targets), as long as every `rm` target is spelled as a literal absolute path (no variable, `~`, glob, backslash or command substitution; `rm -rf "$DIR"` asks), the `rm` is its segment's own command (not behind `xargs`, `find -exec`, `sudo` or `env`), and every other part of the command is, as written, one of `cd <literal path>`, `echo`, `printf`, `true`, `false`, `:`, `test`, `[`, `ls`, `pwd`, with no backtick and no parenthesis anywhere (zsh runs code from `=(cmd)` and glob qualifiers such as `word(e:'cmd':)`; `echo "done (ok)"` therefore asks too). The `rm` may redirect only to a literal absolute path or duplicate an fd (`2>/dev/null`, `2>&1`; zsh reads `<->` as a numeric glob), and at most 16 targets pass this way. Anything else in the same command (`cp`, `mv`, `ln`, `rsync`, `tar`, `install`, `rename`, an interpreter, `sh -c`, a pipe into another program) keeps the code requirement: it could put a non-temp tree where the `rm` then deletes (`mv <outside> <scratchpad>/x && rm -rf <scratchpad>/x`). Limitations: the check reads the command text at check time. Code the shell builds at run time is outside it: a `$` in an rm target, a `cd` argument or a redirection, a parenthesis or a backtick already disables the exemption, but expansions in an allowlisted command's other arguments (`echo ${!x}`, `printf -v`) and zsh-only syntax without `$`, backtick or parentheses are not judged. A background job started by an earlier call can still change the filesystem before `rm` runs, which is why only direct children of the scratchpad qualify. Every other recursive `rm` still needs a code. The main session's code-free removal of a merged-clean lane worktree (`git worktree remove --force` or `rm -rf` of a direct child of `.claude/worktrees/`) does not see an unregistered nested repository in an ignored directory of the lane (`git init` under `node_modules/`): it is deleted with the lane. A nested worktree that `git worktree list` shows makes the removal ask for a code. The code-free lane cleanup needs git 2.36 or later (`git worktree list -z`); with an older git every lane removal asks for a code (fail closed).

## Adopting an existing AI setup

Run `/memokit:init` in a repo that already has an AI setup (a `CLAUDE.md`, an `AGENTS.md`, Cursor/Copilot/Windsurf/Devin/Cline/Roo/Gemini/Kiro/Continue/Junie/Zed/Aider rules, `.claude/` agents, skills, commands, rules or hooks, or legacy per-repo `.claude/hooks/`). Adopt mode refuses to run on a dirty working tree and writes nothing until you approve one table. Every piece of content (a section, a rule, a command) is one row with a target or "kept in place":
- **Moved** (Claude-owned: root `CLAUDE.md`, `.claude/rules|agents|commands|skills`, project and legacy hooks): the content goes into memokit's structure (`CLAUDE.md`, `.claude/rules/<name>.md`, `.claude/memokit/rules.md`, `gates.md`, `coder.md` and the other overlays), then the original is edited or removed as the table says.
- **Copied** (other tools' files): usable content is copied and tagged `(source: <path>)`; the source file stays byte-identical unless you set its row to "remove the source".
- **Kept**: nested `CLAUDE.md`/`AGENTS.md` (checked for conflicts only), personal files (`CLAUDE.local.md`, `.claude/settings.local.json`, except the approved Artifact deny), framework artifacts (`docs/superpowers/`, `.specify/`, `openspec/`, ...), `.mcp.json`, output styles, and project hooks that do not inject context (e.g. a formatter).
- **`AGENTS.md` is never edited.** `CLAUDE.md` imports it with `@AGENTS.md`; Claude reads `AGENTS.md` natively only when no `CLAUDE.md` exists, so the import keeps it read (or starts it being read). Items that contradict memokit's working model go into a short override section right below the import.
- **Scoped rules** become `.claude/rules/<name>.md` with `paths:` frontmatter (from Cursor `globs`, Copilot `applyTo`, and so on). `.claude/memokit/rules.md` is for short, hard rules only and stays small (about 1.5 KB) because it is appended to every prompt.
- **Conflicts** (main session editing code, committing to main, E2E after every change, auto-commit/push hooks, code-writing project agents, superpowers steps that dispatch implementers) are shown with the memokit rule they contradict and are not carried over; you accept or cancel, there is no keep option. Context-injecting project hooks are read, classified and dropped from `settings.json` once their text has a home.
- The table ends with a before/after size summary of what is loaded per prompt and per session. The result is a single commit, only after you approve the diff; roll back with `git revert`.

With legacy per-repo hooks (detected by the memokit-style `inject-rules.sh` signature), adopt mode also extracts the constants (guarded dirs, tag, header, docs, custom hint patterns, rules text) into `memokit.json` and `rules.md`, and removes the old `.claude/hooks/`, `.claude/agents/`, `.claude/skills/handoff|resume` and the `settings.json` hook wiring. A project's own `.claude/hooks/` without that signature is treated as ordinary project hooks.

## Destructive commands

`guard-destructive.sh` denies a Bash command that matches a builtin pattern (`git push --force`/`-f`/`+ref`, `git reset --hard`, `git clean -f` (also with `-n`/`--dry-run`), `git branch -D` (also `-d -f`, `--delete --force`, `-df`), `git worktree remove --force`/`-f` (label `git-worktree-force`: it can discard a worktree's uncommitted work; a plain `git worktree remove` and `git branch -d` are not blocked), `git checkout -- .`/`git restore .` (`git restore --staged` alone is not blocked, nor is `git rm`), recursive `rm` outside `node_modules bin obj dist build .next coverage TestResults __pycache__ .pytest_cache`, `DROP`/`TRUNCATE`/`DELETE FROM` together with a SQL client (psql, pgcli, mysql, mariadb, sqlite3, sqlcmd), `dropdb`, `mysqladmin … drop`, `dotnet ef database drop`, `kubectl delete`, `helm uninstall|delete|del|un`, `docker system|volume prune`, `docker volume rm|remove`; docker global options are tolerated; unique abbreviations such as `git push --fo`, `git reset --ha` and `rm --rec` count, and the command names rm, git, kubectl, helm, docker and dotnet match in any case and with `.exe`) or a project pattern from `careful.patterns`. Quoted, escaped, prefixed and grouped spellings are matched as the command they run (`"rm" -rf x`, `r''m`, `\rm`, `sudo rm`, `timeout 5 rm`, `{rm,-rf,x}`, `(cd x && git reset --hard)`, `git push -f&`, zsh `/bin/rm(N)`), and a computed command word right before an rm-style recursive option (`$RM -rf x`, `/bin/r? -rf x`) counts as a recursive rm. A command longer than 64 KiB, or with more than 1000 distinct rm commands, is not checked but denied as `too-large` (write long files with the Write tool, or approve it). The deny message carries a 6-character code. To approve, start your next message with `onay <code>` or `approve <code>`; the AI then re-runs the exact same command once. A code is bound to the project and the exact command text and expires after 10 minutes. Edit, Write, MultiEdit and NotebookEdit to memokit's approval (grant) file are denied too, including through symlinks and in any letter case, so the AI cannot grant itself an approval; a Bash command naming that file in any case, also through a glob that keeps its name (`careful?grants`, `careful*grants`), is denied without a code, and so is a glob on a `memokit-` path in a temp location (`/tmp/memokit-*`, `$TMPDIR/memokit-*`) or next to `careful`; any other glob that may reach it (`careful*`, `../memokit-*`) is denied as `careful-state-glob`, which can be approved. Every deny message lists all labels the command matched.

It denies rather than asks because a hook's "ask" does not reliably prompt in auto mode or `claude -p`. It is an accident-prevention guardrail, not a sandbox, and the AI runs as your user. The approval code is derived from the project and the command text, so it is not a secret: it stops accidents, not an agent that deliberately works around it. Project patterns can only add to the builtin set. If another memokit guard also blocks the same command (a write to a guarded directory from the main session, git history commands from a subagent), an approval code does not help: that guard's rule applies.

Limitations: matching is on the command text only. A command name that exists only at run time is not seen (`$X push -f`, `$GIT reset --hard`, `$(printf %s r m) -rf x`, zsh `/bin/r(m|x) -rf x`, `$RM src -rf` with the option after an operand, `${~y}` or `${y@P}` expanding to a command, zsh subscript math `$a[z]` with `z` holding a command substitution, SQL spelled `DROP${IFS}TABLE` or `DROP/**/TABLE`), nor is anything run from a script file, an alias or function, or a variable (`bash -c "$CMD"`). A shell that computes the grant file's path at run time (variables, `printf`) can still reach it: the approval code is an accident guard, not a security boundary against a deliberately adversarial agent. A glob on any `memokit-` path (e.g. `ls ../memokit-*`, which also matches memokit-NNN directories) asks for an approval code (`careful-state-glob`); spelling the path out avoids it. False positives are accepted and ask for an approval code: quotes are not parsed, so quoted text is matched like a command (a commit message mentioning `git push --force` or `rm -rf`), and a computed command word (any word the shell computes: `$X`, a glob such as `*` or `?`, `[..]`) directly followed by an option made of rm's letters with `r`/`R` (`"$EDITOR" -R notes.md`, `sudo grep -n "$p" -r src`, `LC_ALL=C grep -n "a.*" -r src`, `sed -n "s/$X/y/" -r f`, `git ls-files | grep -n "x.*" -r`, `tar -C "$d" -rvf a.tar`, `rg "a.*b" -r x f`) counts as a recursive rm, except for a command that is one line and a single segment (no newline, so a backslash-continuation line is never exempt, and no `;`, `|`, `&&`, ` & `, also inside quotes, since quotes are not parsed) whose first word is exactly one of `grep egrep fgrep jq ls cat head tail wc diff cp` (`grep -n "a.*" -r src`, `ls *.log -R`, `jq '.[]' -r f.json` are not denied, 0.7.2; scanned in review for an option that runs a program on macOS/BSD; the GNU variants were not measured) and holds no backtick, `(`, `)`, backslash, `<`, `>` or `&` at all (redirections are never exempt: `grep x $D -r >out` asks for a code), and in which every `$` is followed by a letter or `_` (plain `$NAME`/`"$NAME"`; `${p}`, `$[..]`, `$(..)`, `$1`, `$'..'`, `'x$'` and a trailing `$` are refused). The exemption exists only when the effective locale (`LC_ALL`, else `LC_CTYPE`, else `LANG`) is empty, `C`, `POSIX` or UTF-8, because in a double-byte locale (Big5, GBK, GB18030) a lead byte can swallow the next character; there the 0.7.1 rule applies to every command. It also relies on Claude Code's Bash tool, where `grep` is a shell function running the embedded ugrep, whose `--filter`, `--pager` and `--view` options run programs: Claude Code's shim falls back to the system grep when they appear (measured 2026-11-05 with ugrep 7.8.4; ugrep rejects abbreviations), and a future shim without that fallback would break the premise. Everything else asks for a code: `yq` (mikefarah's system operator, python yq runs `jq`), `sed`, `awk`, `ag`, `tar`, `git grep|log`, `rg` (their options can run a program, and option names can be built at run time), an absolute path (`/usr/bin/grep`), a leading `NAME=value`, a pipeline or list, a regex with parentheses (`grep -rn "func(.*)" -r .`). A failing or silent tool in the check (awk, sed, grep, tr, jq) denies the command instead of letting it through: as `unparsed`, as `careful-state` (no approval possible) when the approval-file check itself cannot run, or with a static message when jq fails.

## Remote changes

Opt-in: nothing here is active until `.claude/memokit.json` has a `remote` object (the `/memokit:init` question writes it). Without it the guard behaves as in 0.7.x.

The AI may do a deploy push or a server change itself, inside a **change window** you approve, instead of asking you for a command or a `!` terminal line.

- **Read-only is free.** `ssh <host> 'systemctl status app'`, `ssh <host> tail …`, `scp`/`rsync` downloads, `rsync --dry-run`, `kubectl diff`/`--dry-run`, `git push --dry-run` need nothing. The builtin read-only first words are `cat ls ll head tail wc df du free uptime whoami id printenv stat grep egrep fgrep ps netstat dig nslookup test true echo pwd which type file md5sum sha256sum systemctl-status systemctl-is-active systemctl-list-units docker-ps docker-logs docker-inspect docker-images docker-stats docker-compose-ps kubectl-get kubectl-describe kubectl-logs kubectl-top git-status tmux-ls`; add more with `remote.readOnlyFirstWords`. Not on the list because they can change the server or run another program: `less env date find curl wget top htop ss ip ifconfig hostname journalctl git-log git-diff git-show` (`ssh prod env`, `ssh prod find / -delete`, `ssh prod git log -1` need a window). An `ssh` with no remote command is free only with `-N`, `-G`, `-V`, `-Q` or `-O check|exit`; a plain `ssh prod` or `ssh -T prod` opens a shell and needs a window. A remote command that is not one plain segment (`ssh prod 'systemctl status app; rm -rf /srv'`, also a separator in quotes or escaped: `ssh prod cat x '&&' rm -rf /srv`, `ssh prod cat x \; rm -rf /srv`) is not read-only.
- **A change needs a plan.** Four labels count as a remote change: `deploy-push` (a push, `gh pr merge` or `gh workflow run` that targets a `remote.deployBranches` branch; a push with no refspec is judged by the current and upstream branch), `remote-mutate` (`ssh`/`scp`/`sftp`/`rsync` to a configured host; with `"*"` any host, and a destination the shell computes, `ssh $H`, gets the target `host:(computed)`, which no window holds: an ordinary code approves that exact command once), `k8s-mutate` (`kubectl apply|create|replace|patch|edit|set|scale|rollout|label|annotate|cordon|uncordon|drain|taint|exec|cp|delete|run|expose|autoscale|debug|attach|certificate`, `helm install|upgrade|rollback|uninstall|delete|del|un`; `kubectl delete` and `helm uninstall` keep their own labels too and carry a `k8s` target) and `runbook` (a file under `remote.runbooksDir`, run directly or through `bash`/`sh`/`zsh`/`source`/`.`). The guard denies the command and the AI presents a **change plan** (targets, what changes, rollback, verification, dry-run output; no command list) and stops.
- **One approval, one window.** Answer `onay <code>`, `onaylıyorum <code>`, `approve <code>` or `approved <code>` on the first line of your message, or just `onaylıyorum` (also `onay`, `approve`, `approved`, `evet onayla`): a bare approval grants the single pending code, and does nothing when there is none or more than one. The window opens for the targets in the plan for `remote.windowMinutes`; the grant message names the targets and the expiry. Pending codes and windows belong to one Claude Code session: a second session in the same project gets its own deny and code. Inside it the AI runs every step in the foreground without asking again. For a plan with several targets the AI first runs `"${CLAUDE_PLUGIN_ROOT}/hooks/memokit-window.sh" request <target>…` (targets: `host:<name>`, `branch:<name>`, `k8s` or `k8s:<context>`, `runbook:<path>`, `pattern:<target>`; unknown ones are refused) and gets one code for all of them. The code is derived from the project and the sorted targets (a runbook contributes its file sha256, so editing the file changes the code); a pending code lives 10 minutes.
- **What a window covers.** The four labels for the window's targets, plus every other label in the same segment (`ssh prod 'rm -rf /srv/old'`; the plan must say "force push" for a forced push). A local segment in the same command (`rm -rf ./data && ssh prod …`) is not covered and is denied as before; so is a target outside the window (the deny names it and gives a new code). A background command is denied (`run_in_background`): no hook sees a background failure, so run it in the foreground with a long timeout, or split it.
- **A failure closes the window.** `close-window.sh` runs after every Bash command; when a command that passed through the window fails, the window is closed and the next deny says so: the AI reports the failure and agrees the next step with you, it does not improvise. A different action is a new plan and a new approval. A failed read-only verification is not seen by the hook; WORKING-MODEL §10 covers it.
- **Afterwards** the AI measures the verification, shows it and appends one row to `remote.log` (default `docs/DEPLOYS.md`): `| date-time | code | targets | plan title (runbook name + hash) | result | verified by |`. The next handoff commits it.
- **Subagents can never do this.** Any subagent segment with one of the four labels is denied (no read-only exemption, regardless of a window), and a subagent cannot run `memokit-window.sh` or edit `.claude/memokit.json`. Approvals belong to the orchestrator.
- **Other tools** (flyctl, vercel, ansible): add a project pattern with a target, for example `{ "match": "\\bflyctl\\s+deploy\\b", "label": "fly-deploy", "target": "fly" }`; a window for `pattern:fly` covers it.

Limitations: it is text matching, not a sandbox (see "Destructive commands"). A runbook is the approved unit: the commands it runs as child processes are not seen, which is why its sha256 is part of the plan. A `~/.ssh/config` alias must be listed by alias (or use `"*"`); the guard does not resolve it. `gh pr merge` and `gh workflow run` count for every deploy branch (the base branch is not looked up, that would be a network call). A covered command with more than 20 segments (1 plus its `;`, `|`, `&` and newline characters, `&&` counted once) is not passed through a window (the hook has 5 s) and gets the change-plan deny with a note that it cannot pass as written. With `remote` configured, a command over 8 KiB, with a piece over 4 KiB between separators, more than 40 pieces, 32 `ssh`/`scp`/`rsync`/`git`/`gh`/`kubectl`/`helm` words or 64 quote characters is not scanned but denied as `too-large` (approvable). `MEMOKIT_CAREFUL_OFF=1` switches all of this off with the guard.

Known gaps, all of them text-matching limits (a window is never opened by them, but a command can pass unlabelled):
- **Hosts the shell computes.** With a host list (not `"*"`), a destination held in a variable or built at run time is not seen: `h=prod.example.com; ssh $h reboot`, `ssh pr${X}od.example.com reboot`. Other spellings of the same address are not resolved either: `ssh 529867170 reboot` for host `31.210.53.162`, a `~/.ssh/config` alias. Use `"*"` (every host, and a computed destination asks for a code) when that matters. A git subcommand or verb held in a variable (`$G $P` with `G=git P=push`) is the same gap.
- **The subagent config gate is lexical.** `guard-subagent-authority.sh` refuses a subagent's write to `.claude/memokit.json` (and the window-request script) by reading the command text. It does not follow `builtin cd` / `command cd`, `CDPATH`, a chain of relative `cd`s, recursive tools run from the project root (`find . -name '*.json' -exec sed -i …`, `grep -rl … | xargs sed -i …`, `chmod -R a-w .`), parameter-default spellings (`.${X:-c}laude`), `cd -` / `cd ~-`, or the window-request script spelled indirectly. A subagent command over 64 KiB, or with more than 512 words holding `..`, a dollar sign or a backquote, or with more than 512 brace expansions, is denied as too large to check (write long files with the Write tool).
- **Project patterns with a target** (`careful.patterns[].target`) are the project's own regex: inside a window their segment is judged by that regex and the shape rules (no `|`, backtick, parenthesis, redirection, `$` or glob), not by an option allowlist like the builtin tools get, so an option of that tool that runs other code passes a `pattern:` window. Keep the pattern narrow.
- **Settings protection is lexical too.** Subagents may not write `.claude/settings.json`, `settings.local.json`, `~/.claude/settings*.json` or the same under `CLAUDE_CONFIG_DIR` (nor read them through `git diff|log|show|status` or `sed`); a word that could name one (`cp x $OUT/settings.json`, a glob such as `settings.*`) is denied. What the text check cannot see: paths assembled from pieces at run time, link makers other than `ln`, `cp -s` and `symlink` in the same command (archive extraction with `tar`, `unzip`, `cpio`, `rsync`, `git`), a copy of `session-start.sh` under another name or reached through a bare variable (`bash $S`), and an interpreter writing through a comma-named link. For `session-start.sh` the last path component of each word decides, wherever it points (copies sit in old plugin caches and checkouts): the name itself, or a glob or expansion that could match it (`hooks/*start.sh`, `${D}start.sh`, `sess*`), is denied for a subagent, and so is a `$(` or backquote in a command that also names `start.sh` or `session` (`hooks/$(echo session)-start.sh`); `$ROOT/scripts/start.sh` is not. A subagent's `sed` or `git` on `hooks/session-start.sh` is denied too (`bats`, `shellcheck`, `cat` pass), which mostly bites memokit's own development. 
- **Protected files are checked at run time (0.8.1).** The settings files above, `.claude/memokit.json`, the session's config snapshot and the plugin's own installed files are checked at run time too. Subagents may not write memokit's or any other plugin's installed files (`~/.claude/plugins`, `CLAUDE_PLUGIN_ROOT`, the same under `CLAUDE_CONFIG_DIR`); a project that develops memokit with `--plugin-dir <project>` is exempt for its own tree. Around every tool call of a subagent `check-integrity.sh` records a digest of these files (content checksum, executable bit, symlink flag, inode and change time) and compares it afterwards, and again when the subagent stops. memokit reports and restores nothing: the subagent is blocked and told to stop and report, your orchestrator's next tool call is denied once, and your next prompt carries a notice; you decide whether to keep or revert the change. The check costs about 40-55 ms per subagent tool call (60-95 files, median of 21 on macOS with bash 3.2) and about 4 ms for a main-session call, also with 200 000 entries in the temp dir (one file test by name, no directory listing). One case only notifies: a permission rule added to a settings file during a call that you answered with "Yes, and don't ask again" (a permission prompt for that rule and settings file, recorded while the call ran and less than 10 minutes ago, is required, and it backs every parallel call it overlaps, for that one change of the file only; it may come from a parallel call of the same subagent, of Bash, Edit, Write, MultiEdit, NotebookEdit, Read or WebFetch). A Bash rule for a shell, interpreter or wrapper, or with a `*` inside the command (`Bash(python3:*)`, `Bash(npm *)`), or a bounded file or domain pattern (`Edit(src/**)`, `Write(docs/*.md)`, `Read(src/**)`, `WebFetch(domain:*.example.com)`), backed by such a prompt, gets a notice of its own that asks you to confirm you meant it. A rule that names `.claude`, settings, memokit, a plugins path or `CLAUDE_CONFIG_DIR`, or is unbounded (a bare tool name, `Bash(*)`, `Read(**)`, `Read(//**)`, `Read(~/**)`, `Edit(**)`, `Edit(~/**)`), is always the full alert, prompt or not; so is any added rule without the prompt.
- **The config snapshot is one more layer, not a tamper-proof one.** At session start memokit copies the validated `.claude/memokit.json` into the temp dir; hooks judge subagent calls by that copy, so a subagent that edits the live file changes nothing for the session. When the file changes or disappears, the next prompt shows one notice, and `/clear` or a new session adopts the change. The copy is a file of your user in a shared temp dir, so a process running as you can still replace it.
- **The markitdown cache is protected the same way.** Its entries are kept from subagents lexically (the `careful-` state family: a subagent file-tool write below `memokit-<n>-careful-convert` is denied, a Bash command naming it is `careful-state`) and by an ownership check on every hit (the cache dir, the document's dir and the copy must be yours and not symlinks). A process running as you can still replace an entry through an indirection the guards cannot see (a path assembled at run time, a glob that avoids the `memokit-` spelling); the next Read of that document then returns it. A digest of each entry would not help: it would sit where the same user can write too.
- **Limits of the runtime check.** (1) A process running as you can tamper with the integrity records and stamps in the temp dir, or delete them. (2) A change made after a subagent's last tool call that outlives it, or by something that outlives the subagent (a detached process), is seen at the next subagent call or not at all; a background Bash command is not covered. (3) A permission-prompt record proves that a prompt was shown for that call, not that you chose "don't ask again": a command that writes the suggested rule itself looks the same, and you still get the notice. (4) Bash prefix rules for ordinary commands (`npm`, `pnpm`, `yarn`, `git`, `make`) get the plain notice with that evidence; rules for shells, interpreters, wrappers, `find`, `sed`, `awk`, `tar`, `ssh` and similar are not blocked with it either, but get the broad-rule notice that asks you to confirm them; rules naming protected paths or unbounded ones never pass. The evidence is matched by rule, settings file and time, not by the call: a prompt of a parallel call of the same subagent counts. (5) Still lexical and not caught before the call: names of `session-start.sh` assembled at run time, and link makers beyond `ln`, `cp -s` and `symlink`; the runtime check reports their effect afterwards. (6) With `--plugin-dir <project>` only the project tree is exempt, and only when `CLAUDE_PROJECT_DIR` is set and resolves to the project: in such a session a subagent command holding a glob or expansion (`bats tests/*.bats`) is denied unless it is read-only, and only exact project spellings pass. The rest of such a checkout (its other worktrees, its own files outside the project tree) stays in the runtime check, so an edit that another session makes there while a subagent call runs is reported as a change during that call. (7) The check that a subagent does not write memokit's state files through a hard link walks the temp dir; on a very large temp dir it adds time to every subagent file write.
- **Push options inside a window are an allowlist.** Unusual `git push` options (anything outside the common set: `-u`, `-f`, `--force-with-lease`, `--tags`, `--dry-run`, `-o`, …; also `-4`, `-6`, `--thin`, `--signed`) are not covered by a window and ask for a code. A window never covers a push that deletes or mirrors refs.
- **State files** (`careful-pending-*`, `careful-window-*`, `careful-active-*` under `$TMPDIR`) are removed when read after they expire (a record that expires further out than its time to live counts as malformed and goes too), and SessionStart prunes state files older than 7 days once a day; up to five small files per session stay behind until then. A write into a `memokit-` state path that the shell computes is `careful-state`, but the GNU `cp`/`mv`/`ln`/`install -t DIR` form (destination first; Linux only) is not labelled.
- **Accepted false denies of the ANSI-C (`$'…'`) decoding** (fail closed): with `remote` configured, a command whose quotes the decoder cannot follow is denied as `unparsed` (approvable with its code): a `#` comment holding a `$'` (`ls # $'x'`), and an unbalanced quote next to a `$'…'` span (`echo 'it\'s' $'x' …`; the backslash does not escape inside single quotes, so the quotes stay open). Write such text without `$'` or approve the code.

## Türkçe

memokit, Claude Code için bir çalışma modeli plugin'idir: ana oturum (orkestratör) üretim kodu yazmaz, kodu bir Sonnet alt ajanı (`memokit:coder`) yazar, her dilimi bir Opus gözden geçirici (`memokit:reviewer`) onaylar. Oturum ritüelleri `docs/STATE.md` dosyasını güncel tutar; bağlam bütçesi aşılınca yapay zekâ kendi kararıyla ölçülü bir handoff yapar.

memokit'i **bir kez, kullanıcı düzeyinde** kurun:

```
/plugin marketplace add tsrmehmet/memokit
/plugin install memokit@memokit
```

`/plugin install` penceresinde kullanıcı kapsamını seçin (kabukta: `claude plugin install memokit@memokit --scope user`). Manifest `"defaultEnabled": true` ayarladığı için kurulumla birlikte memokit her projede etkin olur. `.claude/memokit.json` olmayan projelerde hook'lar sessiz kalır, `memokit:` önekli ajan ve skill'ler kendiliğinden durur; "`/memokit:init` çalıştırın" ipucu varsayılan olarak kapalıdır (`MEMOKIT_INIT_HINT=1` açar). `/memokit:init`, depoyu klonlayan herkese de memokit önerilsin mi diye sorar; yalnız evet cevabında projenin paylaşılan `.claude/settings.json` dosyasına `enabledPlugins["memokit@memokit"] = true` ve marketplace kaydını yazar. Önerilen cevap, depoyu siz yönetmiyor ve ekip onaylamadıysa hayırdır: bu kayıt her katkıcıya üçüncü taraf bir eklenti önerir, sizin için kullanıcı kapsamlı kurulum zaten yeterlidir. Güvenmediğiniz bir depoda ilk oturumdan önce `.claude/memokit.json` dosyasına bakın: `sessionStart.healthScript` her oturum başında, `graph.refreshScript` handoff'ta çalışır (deponun `.claude/settings.json` hook'larıyla aynı risk; memokit yalnız proje kökünün dışına çıkan betikleri reddeder).

Ardından memokit'i kullanacağınız git deposunda `/memokit:init` çalıştırın; proje adı, etiket, dil, korunan klasörleri ve kod grafiğini (graphify) sorar, `.claude/memokit.json` dosyasını yazar. `graph` ayarlıysa her handoff kod grafiğini tazeler (yalnız kod, LLM yok); handoff'un son adımı telefonuna bildirim gönderir (Remote Control bağlıyken). Türkçe yanıt ve hook mesajları için `memokit.json` içinde `"language": "tr"` ayarlayın. Acil durumda korumaları kapatmak için `MEMOKIT_GUARD_OFF=1` değerini `.claude/settings.local.json` içindeki `env` bölümüne yazın ya da `claude`'u başlatmadan önce dışa aktarın. Kişisel bir altyapıdır, olduğu gibi paylaşılır; destek garantisi yoktur. Yıkıcı komutlar (force push, reset --hard, özyinelemeli rm, yıkıcı SQL, kubectl/helm delete ve projenin `careful.patterns` kalıpları) engellenir; onay için bir sonraki mesajınıza `onay <kod>` ile başlayın. Bu bir kaza önleme korkuluğudur, sandbox değildir: yalnızca komut metnine bakar. 64 KiB'tan uzun (ya da 1000'den fazla rm komutu içeren) bir komut denetlenmez, `too-large` olarak engellenir; uzun dosyaları Write aracıyla yazın ya da onay kodu verin. Kırmızı ve flaky testler için `/memokit:triage`. PDF, DOCX, PPTX ve XLSX dosyaları isteğe bağlı olarak markitdown ile Markdown okunur (`"convert": {"markitdown": true}`; markitdown'ı siz kurarsınız: `uv tool install 'markitdown[pdf,docx,pptx,xlsx]'`); taranmış PDF'ler, görseller ve sohbete yapıştırılan ekler eskisi gibi okunur ("PDF and Office files").

Birden çok bağımsız görev için `/memokit:parallel`: her şerit (lane) kendi git worktree'sinde çalışır (aynı deponun, kendi dalı ve dosyaları olan ayrı bir çalışma klasörü; şeritler birbirinin dosyasının üzerine yazamaz). Akış: analiz → plan onayı → öngörülen tüm kararlar tek seferde sorulur → en fazla `parallel.maxCoders` şerit aynı anda → riske göre gözden geçirme (`high` Opus, `normal` Sonnet; `review.model`) → sırayla birleştirme → worktree ve dalın hemen temizlenmesi → Opus ile tüm batch'in gözden geçirilmesi → Tier 2 sorusu. Testler iki katmanlıdır (WORKING-MODEL.md §9): Tier 1 (build + birim testleri + dilimin yeni testleri) her dilimde; ağır kapılar (Tier 2) batch başına bir kez ve yalnız kullanıcı onaylarsa. Komutlar `.claude/memokit/gates.md` dosyasındadır. Koşunun durumu git'e girmeyen yerel bir ledger dosyasında tutulur, handoff ve resume onu sürdürür. Artakalan worktree ve `mk/*` dalları oturum başında raporlanır; 0.6.1'den beri birleşmiş, temiz ve `scratch.staleAfterHours` boyunca kullanılmamış olanlar ile önceki oturumların eski temp dosyaları arka planda otomatik silinir (`MEMOKIT_AUTOCLEAN_OFF=1` kapatır); geri kalanları `/memokit:sweep worktrees` onayınla siler, birleşmemiş ya da değişiklik içeren iş hiçbir zaman otomatik silinmez; etkin bir koşunun (ledger `status: active`) şeritleri artakalan sayılmaz, oturum başı o koşuyu adıyla anar. `git worktree remove --force` bir onay kodu ister (`git-worktree-force`).

0.5.x'ten yükseltirken: test komutlarını `coder.md` dosyasından `.claude/memokit/gates.md` dosyasına taşıyın (`## Tier 1`: build + birim testleri, zaten çalışan bir dev container'a exec dahil; `## Tier 2`: entegrasyon, container başlatma, Docker paketleri, E2E) ve `coder.md` içindeki dilim başı ağır kapıları kaldırın; ya da bunu bir sonraki oturuma bırakın, `/memokit:resume` bir kez sorar. Ayrıntılar: "Upgrading from 0.5.x".

0.8.0'dan beri: `memokit.json` içinde `remote` varsa orkestratör deploy dalına push ve sunucu değişikliklerini kendisi yapar. Salt okuma serbesttir; değişiklik için plan sunar, siz `onay <kod>` ya da yalnızca `onaylıyorum` dersiniz, plandaki hedefler için bir pencere açılır ve adımlar tekrar sormadan çalışır. Bir adım başarısız olursa pencere kapanır ve size rapor verir. Komutu size vermez, alt ajanlar bunu hiçbir zaman yapamaz ("Remote changes"). Orkestratör kendi temp klasörlerini ve birleşmiş, temiz şerit worktree'lerini ve dallarını onay kodu olmadan siler.

Zaten bir yapay zekâ kurulumu olan projede (CLAUDE.md, AGENTS.md, başka araçların kuralları, `.claude/` ajan/skill/hook'ları, eski per-repo hook'lar) `/memokit:init` benimseme (adopt) kipine girer: temiz çalışma ağacı ister, tek bir tablo gösterir ve onayınıza kadar hiçbir şey yazmaz. Claude'a ait kaynaklar memokit yapısına taşınır; diğer araçların dosyaları bayt bayt aynı kalır (içerik `(source: ...)` etiketiyle kopyalanır); `AGENTS.md` asla düzenlenmez, `CLAUDE.md` onu `@AGENTS.md` ile içe aktarır ve çelişen maddeler hemen altında bir geçersiz kılma bölümünde listelenir. Belirli dosya kalıplarına bağlı kurallar `paths:` ile `.claude/rules/` altına gider; `rules.md` her istemde eklendiği için küçük (yaklaşık 1,5 KB) tutulur. Kişisel dosyalara (`CLAUDE.local.md`, `.claude/settings.local.json`) dokunulmaz; tek istisna onayladığınız Artifact deny kuralıdır. Sonuç tek bir commit'tir; geri almak için `git revert`. Ayrıntılar: "Adopting an existing AI setup".
